# Архитектурное решение по трейсингу

Документ описывает, как в системе «Александрит» увидеть путь каждого заказа через магазин, CRM, очередь и MES, найти место, где заказ завис или потерялся, и построить на этих данных автоматический контроль.

Схемы:

- [alexandrite-tracing.png](diagrams/alexandrite-tracing.png): системы, покрываемые трейсингом, и новые компоненты (красным); исходник [alexandrite-tracing.drawio](diagrams/alexandrite-tracing.drawio).
- [alexandrite-tracing-alerting.png](diagrams/alexandrite-tracing-alerting.png): та же схема плюс автоматический контроль прохождения заказа и алертинг (зелёным); исходник [alexandrite-tracing-alerting.drawio](diagrams/alexandrite-tracing-alerting.drawio).

## 1. Анализ системы: где заказ может сломаться или зависнуть

Заказ проходит через три приложения и очередь, а его статус меняют разные системы. Точки, в которых заказ может «сломаться», собраны в таблице.

| № | Место | Что происходит | Как ломается |
| --- | --- | --- | --- |
| T1 | Shop API: сохранение заказа и загрузка файла в S3 | Два действия в разных хранилищах | Файл не загружен, заказ есть; заказ не сохранён, файл есть. Заказ в SUBMITTED, который нельзя посчитать |
| T2 | Передача заказа из магазина в CRM | Обе системы работают с одной базой, явного вызова нет | CRM не «увидела» заказ (фильтр, статус, ошибка задания), заказ никогда не уходит на расчёт. Самый непрозрачный переход в системе |
| T3 | CRM API публикует заявку на расчёт в RabbitMQ | Publish без подтверждений | Сообщение не дошло до брокера или не пережило рестарт; CRM считает, что отправила |
| T4 | MES API получает заявку, скачивает файл, считает стоимость | Долгая операция, 2-30 минут | Consumer упал во время расчёта; истёк таймаут подтверждения; сообщение переотправлено и посчитано дважды; файл не скачался |
| T5 | MES API публикует PRICE_CALCULATED, CRM API обновляет Shop DB | Обратный путь через очередь | Те же потери, что в T3; дубликат статуса; статус применён к не тому заказу |
| T6 | Продавец подтверждает производство, CRM API отправляет MANUFACTURING_APPROVED | Ручной шаг плюс очередь | Заказ подтверждён в CRM, но не появился у операторов |
| T7 | Операторы меняют статусы в MES, MES API отправляет их в CRM | Несколько сообщений на заказ | CRM видит устаревший статус, менеджер обещает клиенту неверные сроки |
| T8 | Партнёрский сценарий: вызов MES API, расчёт, создание заказа в CRM по сообщению | Заказ рождается «с конца» | Партнёр не получил ответа; заказа в CRM нет, хотя расчёт выполнен; невозможно понять, какой запрос партнёра к какому заказу относится |
| T9 | Закрытие заказа по сообщению транспортной компании | Внешняя интеграция | Сообщение не пришло или не разобрано, заказ висит в SHIPPED |

Системы, которые нужно покрыть трейсингом (на схеме выделены красной рамкой):

1. **Shop API**: рождение заказа, загрузка файла, момент передачи в CRM (T1, T2).
2. **CRM API**: producer и consumer сообщений, изменение статусов, подтверждение производства, закрытие заказа (T2, T3, T5, T6, T9).
3. **MES API**: consumer заявок на расчёт, сам расчёт, загрузка файла из S3, producer статусов, партнёрские запросы, действия операторов (T4, T5, T7, T8).
4. **RabbitMQ** как транспорт контекста: брокер сам не инструментируется, но каждое сообщение переносит идентификаторы трассы и заказа в заголовках, иначе путь заказа рвётся на каждой очереди.
5. Обращения к **Shop DB, MES db и S3** покрываются автоматически как клиентские спаны внутри трёх API. Отдельной инструментации на стороне баз не требуется.

В первую очередь не покрываются: фронтенды (спаны из браузера полезны, но требуют отдельной работы с CORS и персональными данными), интеграция с транспортной компанией (внешняя система, доступен только факт получения сообщения) и Яндекс Метрика.

## 2. Данные, которые должны попадать в трейсинг

Используются соглашения OpenTelemetry (semantic conventions), чтобы стандартные инструменты понимали данные без настройки.

Идентификаторы и связи:

- `trace_id`, `span_id`, `parent_span_id`; для обработчиков ссылка (span link) на спан отправителя, если сообщение обрабатывается сильно позже отправки;
- `order.id` во всех спанах, которые касаются заказа. Это главный ключ поиска: «покажи всё, что происходило с заказом 12345»;
- `correlation.id` запроса партнёра, чтобы связать вызов API и заказ, созданный по нему в CRM.

Атрибуты ресурса (описывают, кто отправил спан): `service.name` (shop-api, crm-api, mes-api), `service.version`, `deployment.environment` (dev, release, prod), `host.name`.

Атрибуты спанов по типу операции:

| Тип операции | Данные |
| --- | --- |
| HTTP-запрос (server, client) | метод, маршрут-шаблон, код ответа, длительность; для партнёрских маршрутов `partner.id` (идентификатор учётной записи партнёра) |
| Сообщение очереди (producer, consumer) | `messaging.system=rabbitmq`, exchange, routing key, имя очереди, `messaging.message.id`, операция (publish, receive, process), признак redelivered, номер попытки |
| Запрос к базе (client) | `db.system=postgresql`, имя базы, текст запроса без параметров, длительность |
| Обращение к S3 (client) | операция (get, put), bucket, ключ объекта, размер файла, длительность |
| Расчёт стоимости (internal) | `order.id`, `model.file_id`, `model.polygons`, `calc.duration`, результат (успех, ошибка, таймаут), версия алгоритма расчёта |
| Смена статуса заказа (internal) | `order.id`, `order.status.from`, `order.status.to`, `order.source` (shop, api), кто инициировал (система, идентификатор сотрудника, идентификатор партнёра) |
| Ошибки | статус спана error, тип исключения, сообщение без чувствительных данных, стек в событии спана |

Что в трейсинг не попадает: персональные данные покупателей (имя, телефон, почта, адрес), тела запросов и файлы моделей, токены и ключи API, параметры SQL-запросов. Покупатель и партнёр представлены только внутренними идентификаторами.

Особенность процесса: заказ живёт недели, а трасса покрывает операцию длиной в секунды или минуты. Поэтому одному заказу соответствует не одна трасса, а цепочка трасс (создание, расчёт, подтверждение, каждый производственный статус), связанных через `order.id`. Чтобы цепочку можно было собрать одним запросом, в журнал статусов заказа (таблица истории переходов в Shop DB, которую ведёт CRM API) на каждый переход записывается `trace_id`. Из карточки заказа в CRM появляется ссылка «показать путь заказа».

## 3. Мотивация

Сейчас команда видит, что заказы находятся в непонятном состоянии или зависли, но не видит, где именно. Разбор жалобы сводится к ручному сопоставлению записей в двух базах и переписка с партнёром. Трейсинг даёт три вещи:

1. Один запрос по `order.id` показывает всю цепочку: где заказ был, сколько занял каждый шаг, на каком шаге произошла ошибка или на каком шаге цепочка оборвалась (есть спан publish, но нет спана process: сообщение потеряно).
2. Данные для проверки гипотез из планирования: действительно ли теряются сообщения, действительно ли расчёты упираются в таймаут, сколько времени занимает передача заказа из магазина в CRM.
3. Основа для автоматического контроля: если по спанам известно, что заказ вошёл в статус SUBMITTED и за час не появился спан расчёта, об этом можно сообщить, не дожидаясь жалобы.

Метрики, на которые повлияет внедрение:

| Метрика | Тип | Сейчас | Цель после внедрения |
| --- | --- | --- | --- |
| Время локализации проблемы с заказом (от обращения до понимания, на каком шаге он застрял) | техническая | часы, иногда дни | минуты |
| Доля сообщений, потерянных между системами (спан publish без парного спана process) | техническая | неизвестна, измерить нечем | измеряется, цель менее 0,1 %, затем 0 |
| p95 длительности каждого шага заказа (расчёт, передача в CRM, создание партнёрского заказа) | техническая | неизвестна | измеряется по спанам, входит в SLO |
| Доля заказов, застрявших дольше нормы шага, и время до их обнаружения | бизнес и техническая | обнаруживаются по жалобам через недели | обнаружение за час, доля застрявших менее 1 % |
| Количество обращений «где мой заказ» на 100 заказов и время ответа на них | бизнес | растёт вместе с числом заказов | снижение в разы, ответ по данным, а не по расследованию |
| Время от вызова партнёрского API до появления заказа в CRM | бизнес | неизвестно, жалобы ежедневно | измеряется, основа SLA партнёрам |

## 4. Предлагаемое решение

### 4.1. Технологии

- **OpenTelemetry** как стандарт сбора: единый формат для Java и C#, W3C Trace Context для передачи контекста, готовые библиотеки инструментирования для Spring, ASP.NET Core, JDBC, Npgsql, HTTP-клиентов, RabbitMQ и AWS SDK (S3). Не привязывает к вендору хранилища.
- **OpenTelemetry Collector** как единая точка приёма: приложения знают только адрес коллектора, а куда и как отправлять трассы дальше, решается в его конфигурации.
- **Grafana Tempo** как хранилище трасс: хранит данные в Object Storage (дёшево, без отдельной базы), ищет по атрибутам (TraceQL), встроен в Grafana, которая уже используется для метрик. Альтернатива Jaeger с хранилищем в OpenSearch рассматривалась: она уместна, если команда решит хранить трассы и логи в одном OpenSearch, но добавляет нагрузку на кластер логов.
- **Grafana** как интерфейс поиска трасс и переходов между метриками, логами и трассами по `trace_id`.

### 4.2. Компоненты, которые нужно внедрить или доработать

Новые компоненты (на схеме красным):

| Компонент | Назначение | Размещение |
| --- | --- | --- |
| OpenTelemetry Collector | Приём спанов по OTLP, батчинг, удаление чувствительных атрибутов, экспорт в Tempo | Две небольшие ВМ или контейнеры в приватной подсети; приложения шлют на балансируемый адрес |
| Grafana Tempo | Хранение и поиск трасс, хранение 30 дней | ВМ в приватной подсети, данные в Object Storage |
| Grafana (общая с мониторингом) | Поиск по `order.id`, просмотр цепочек, ссылки из логов | Уже есть по плану мониторинга |
| Инженер поддержки и разработчик как пользователи | Разбор обращений, отладка | Доступ через SSO |

Доработки существующих систем:

| Система | Что сделать |
| --- | --- |
| Shop API, CRM API | Подключить OpenTelemetry Java agent (автоинструментация Spring MVC, JDBC, HTTP-клиентов, Spring AMQP, AWS SDK без изменения кода). В коде добавить атрибуты `order.id`, `order.status.from/to`, `order.source` в местах создания заказа и смены статусов. В отправителе класть в заголовки AMQP `traceparent`, `tracestate`, `order_id`, `correlation_id`; в обработчике создавать спан process с родителем или ссылкой из заголовков (агент делает это автоматически для Spring AMQP, нужно только проверить, что заголовки не теряются на кастомных обёртках) |
| MES API | Подключить OpenTelemetry .NET (ASP.NET Core, HttpClient, Npgsql, AWS SDK; RabbitMQ.Client 7 поддерживает OpenTelemetry через пакет RabbitMQ.Client.OpenTelemetry, для более старой версии клиента контекст передаётся вручную через заголовки). Обернуть расчёт стоимости отдельным спаном с атрибутами модели и результата. На партнёрских маршрутах добавлять `partner.id` и возвращать партнёру `request_id` (равен `trace_id`) в ответе |
| Переход из магазина в CRM (T2) | Сделать переход явным: Shop API при переводе заказа в SUBMITTED сохраняет в записи заказа `submit_trace_id`, а задание CRM API, которое подхватывает новые заказы, создаёт спан со ссылкой на него. Так самая непрозрачная связь получает свою трассу без переделки интеграции. В целевой архитектуре переход становится событием, которое Shop API публикует в очередь, и контекст уезжает в заголовках сообщения; колонка остаётся для совместимости |
| Журнал статусов заказа | В таблицу истории переходов (CRM API) добавить колонки `trace_id` и `initiator`; в карточке заказа CRM ссылка на поиск в Grafana по `order.id` |
| Коллектор | Процессоры: `memory_limiter`, `batch`, `attributes` (удаление ключей с персональными данными как страховка), `resource` (окружение). Сэмплирование на этапе внедрения 100 % для всех спанов с `order.id`, проверки здоровья не записываются вовсе. Объём при текущих тысячах заказов в месяц измеряется единицами гигабайт, поэтому экономить на сэмплировании рано |

Порядок внедрения: коллектор и Tempo (DevOps, 3 дня), Java agent на CRM API вместе с бизнес-атрибутами и заголовками сообщений (Java, 4 дня), MES API (C#, 5 дней), затем Shop API (Java, 2 дня), явный переход T2 и журнал статусов (Java, 3 дня), обучение поддержки поиску по заказу (1 день). Порядок совпадает с порядком подключения логирования: сначала участок CRM API и MES API, где теряются сообщения. Сначала dev и release, где сравнивается накладной расход (ожидание до 2-3 % CPU), затем prod.

### 4.3. Дополнительное задание: автоматический контроль прохождения заказа и алертинг

Сами трассы отвечают на вопрос «что случилось с конкретным заказом». Чтобы система сообщала о проблемах сама, данные трейсинга превращаются в метрики и правила. Элементы автоматического контроля на схеме [alexandrite-tracing-alerting.png](diagrams/alexandrite-tracing-alerting.png) отмечены зелёным. Prometheus и Alertmanager при этом не новые, они появляются по плану мониторинга; зелёным показаны их новые связи и роль в контроле заказа.

1. **Метрики из спанов.** В коллекторе включается connector `spanmetrics`: по каждому спану он считает количество, ошибки и гистограмму длительности с измерениями `service.name`, операция, `order.status.to`, `order.source`, `partner.id`. Метрики отдаются в Prometheus из плана мониторинга. Так появляются ряды «сколько заказов перешло в PRICE_CALCULATED за 5 минут», «p95 расчёта по партнёру», «ошибки обработчика по очереди» без дополнительного кода в приложениях.
2. **Контроль воронки заказа.** Отдельный компонент Order Flow Monitor (небольшой сервис или задание внутри CRM API) раз в минуту сравнивает журнал статусов с нормативами шага: SUBMITTED без PRICE_CALCULATED дольше 60 минут, PRICE_CALCULATED без решения продавца дольше суток, MANUFACTURING_APPROVED без MANUFACTURING_STARTED дольше двух рабочих дней, партнёрский расчёт без заказа в CRM дольше 15 минут. Результат публикуется как gauge `orders_stuck{stage}` с перечнем идентификаторов в логе. Дополнительно он проверяет парность спанов publish и process по `messaging.message.id` за прошедший час и публикует `messages_lost_total{queue}`. На текущих объёмах (тысячи сообщений в день) такой запрос к Tempo по атрибуту выполняется за секунды; при росте объёмов проверку переносят на события `message.published` и `message.received` в системе логирования, где тот же идентификатор ищется дешевле.
3. **Правила и алерты.** В Prometheus описываются правила: `orders_stuck > 0` (warning, тикет поддержке), `orders_stuck{stage="calculation"} > 10` или заказ старше 4 часов (critical, звонок), `messages_lost_total` вырос (critical), отсутствие переходов в PRICE_CALCULATED 30 минут при наличии новых SUBMITTED (critical), p95 расчёта больше 30 минут (warning). Alertmanager направляет warning в Telegram-канал поддержки и создаёт тикет, critical дополнительно звонит дежурному. В текст алерта подставляются идентификаторы заказов и ссылка на поиск трассы в Grafana.
4. **Дашборд процесса.** В Grafana собирается панель воронки: заказы по статусам, время в каждом статусе, застрявшие заказы, потери сообщений, разбивка по источнику (магазин, партнёры) и по партнёру.

## 5. Компромиссы

Когда трейсинг не принесёт пользы, пока невозможен или обойдётся дорого:

- MES куплена с исходным кодом. Автоинструментация ASP.NET Core не требует правок кода, но бизнес-атрибуты и передача контекста через RabbitMQ требуют изменений в исходниках MES. Каждая правка увеличивает расхождение с версией вендора и делает его обновления дороже. Изменения в MES выделяются в отдельный слой (middleware, обёртки над клиентом очереди), чтобы их можно было переносить между версиями. На единственного C#-разработчика это заметная нагрузка, поэтому найм второго остаётся условием.
- Заказ живёт неделями. Одна трасса не покрывает жизненный цикл. Если ожидать от трейсинга «водопад» на весь заказ, результат разочарует. Цепочка собирается через `order.id` и журнал статусов, и это нужно проговорить с поддержкой заранее.
- Долгие расчёты. Спан расчёта в 30 минут не подходит для tail-сэмплирования (решение о сохранении принимается за секунды после начала трассы) и плохо читается в интерфейсе. Поэтому используется head-сэмплирование 100 % для спанов заказа, а долгие расчёты дополнительно разбиваются на этапы (загрузка файла, подготовка, расчёт, публикация результата).
- Внешние стороны. Партнёры и транспортная компания не передают и не принимают контекст трассы. Для партнёров граница трассы проходит по их запросу к API, взамен они получают `request_id`; для транспортной компании трасса начинается с приёма сообщения.
- Переход через общую базу. Там, где системы общаются через таблицы, вызова нет и трассировать нечего. Решение выше делает переход явным через `submit_trace_id`, но это доработка кода, а не настройка.
- Физический процесс. Между MANUFACTURING_STARTED и MANUFACTURING_COMPLETED работает человек. Трейсинг покажет длительность, но не причину. Здесь нужны данные производства, а не спаны.
- Фронтенды и Яндекс Метрика. Спаны из браузера дали бы полный путь от клика до заказа, но требуют CORS-настроек, фильтрации персональных данных и работы фронтенд-инженеров. Отложено до второй очереди.
- Стоимость и дисциплина. Две-три ВМ, хранение в Object Storage, 1-3 % CPU накладных расходов стоят недорого. Дороже дисциплина: если разработчики не проставляют `order.id`, поиск по заказу не работает. Нужны соглашения по атрибутам и проверка на код-ревью.

## 6. Безопасность

Меры для предотвращения несанкционированного доступа к системе трейсинга:

| Направление | Мера |
| --- | --- |
| Сеть | Коллектор и Tempo размещаются в приватной подсети без публичных адресов. Порты OTLP открыты группами безопасности только для подсетей приложений. Grafana доступна из корпоративной сети или через VPN |
| Приём данных | OTLP по TLS; коллектор проверяет токен приложения (bearer token в заголовке), отдельный токен на окружение. Отправлять спаны может только приложение компании |
| Аутентификация и роли | Вход в Grafana только через корпоративный SSO с MFA. Роли: «Поддержка» видит поиск трасс по заказу и дашборды процесса на prod; «Разработчик» видит всё на dev и release и только чтение на prod; «DevOps» администрирует. Локальные учётные записи отключены, доступ уволенных отзывается через IdP |
| Данные | В спанах нет персональных данных, тел запросов и секретов. В коллекторе процессор `attributes` удаляет заголовки Authorization, Cookie и любые ключи из запрещённого списка как страховка от ошибок инструментирования. Окружения разделены (prod пишет в отдельный тенант Tempo) |
| Хранение | Object Storage с шифрованием на стороне сервиса, хранение 30 дней, автоматическое удаление. Резервные копии не требуются: трассы восстанавливаются заново из работы системы |
| Аудит | Журнал входов и запросов Grafana включён и отправляется в систему логирования; пересмотр прав раз в квартал |
| Снаружи компании | Внешним пользователям (партнёрам, клиентам) система трейсинга недоступна. Партнёр получает только `request_id` в ответе API и статус заказа через API или webhook; по `request_id` поддержка находит трассу сама |
| Доступность самой системы | Алерт на недоступность коллектора и Tempo, чтобы отсутствие трасс не путали с отсутствием проблем; конфигурация в git с ревью |
