# Архитектурное решение по логированию

Документ описывает, какие логи нужно собирать в системе «Александрит», как их собирать и хранить, кто и как получит к ним доступ и как превратить сбор логов в анализ.

Схема: [alexandrite-logging.png](diagrams/alexandrite-logging.png), исходник [alexandrite-logging.drawio](diagrams/alexandrite-logging.drawio). Красной рамкой отмечены системы, из которых собираются логи, красной заливкой новые компоненты.

## 1. Анализ системы: какие логи собирать и откуда

Сейчас ошибки разбираются со слов клиента. Чтобы восстановить, что произошло на стороне сервиса, нужны записи о каждом значимом событии в жизни заказа и о каждой интеграционной операции, причём в одном месте и в одном формате.

Источники логов:

| Система | Что даёт | Приоритет |
| --- | --- | --- |
| CRM API | Смена статусов, подтверждение производства, публикация и обработка сообщений, закрытие заказов | 1 |
| MES API | Обработка заявок на расчёт, расчёт стоимости, статусы производства, запросы партнёрского API, действия операторов | 1 |
| Shop API | Создание заказов, загрузка файлов, передача заказа в CRM | 2 |
| RabbitMQ (логи брокера) | Соединения, ошибки каналов, закрытие по таймауту подтверждения, тревоги по памяти и диску | 2 |
| Managed PostgreSQL (Shop DB, MES db) | Медленные запросы, ошибки, блокировки; доступны через Yandex Cloud Logging | 3 |
| ВМ (системные логи) | Рестарты сервисов, OOM, диски | 3 |
| Фронтенды Internet Shop, CRM, MES | Ошибки в браузере | 4, вторая очередь |

### 1.1. Список логов уровня INFO

Общие поля каждой записи: `timestamp` (UTC), `level`, `service`, `env`, `version`, `instance`, `event` (машинное имя события), `message`, `trace_id`, `span_id`, `request_id`, `order_id` (если применимо), `actor` (идентификатор сотрудника, партнёра или имя системы).

| Событие | Система | Поля записи |
| --- | --- | --- |
| `order.created` | Shop API (заказы магазина), CRM API (заказы партнёров) | время, номер заказа, идентификатор покупателя или партнёра, источник (shop, api), канал |
| `order.file_uploaded` | Shop API | номер заказа, идентификатор файла, размер, формат, ключ в S3, контрольная сумма, число полигонов (если известно) |
| `order.status_changed` | Shop API, CRM API, MES API | время, номер заказа, идентификатор покупателя, статус до и после, инициатор (сотрудник, партнёр, система), причина |
| `order.picked_by_crm` | CRM API | номер заказа, задержка от SUBMITTED до подхвата (закрывает непрозрачный переход через общую базу) |
| `message.published` | CRM API, MES API | exchange, routing key, идентификатор сообщения, номер заказа, correlation id, результат publisher confirm |
| `message.received`, `message.processed` | CRM API, MES API | очередь, идентификатор сообщения, номер заказа, номер попытки, признак redelivered, результат, длительность обработки |
| `message.dead_lettered` | CRM API, MES API | очередь, идентификатор сообщения, номер заказа, причина |
| `calc.started`, `calc.finished` | MES API | номер заказа, идентификатор файла, число полигонов, длительность, результат (сумма, ошибка, таймаут), версия алгоритма |
| `order.assigned` | MES API | номер заказа, идентификатор оператора, время |
| `order.shipped` | MES API | номер заказа, перевозчик, номер отправления |
| `order.closed` | CRM API | номер заказа, основание (сообщение перевозчика, вручную), идентификатор сотрудника |
| `partner.request` | MES API | идентификатор партнёра, маршрут, request id, код ответа, длительность, размер запроса (без тела) |
| `carrier.callback` | CRM API | номер заказа или отправления, статус от перевозчика, результат разбора |
| `http.request` (access log) | все три API | метод, маршрут-шаблон, код ответа, длительность, request id, идентификатор пользователя или партнёра, размер ответа |
| `job.run` | CRM API, MES API | имя задания (подхват заказов, сверка, пересчёт метрик), обработано записей, длительность, результат |
| `app.started`, `app.stopped` | все три API | версия, окружение, краткая сводка конфигурации без секретов |

Правило для INFO: одна запись на одно бизнес- или интеграционное событие. Внутри расчёта стоимости на INFO пишутся только начало и конец, промежуточные шаги идут на DEBUG.

### 1.2. Другие уровни логирования

| Уровень | Когда используется |
| --- | --- |
| DEBUG | Подробности обработки: тела сообщений очереди (без персональных данных), шаги расчёта, параметры запросов к базе. На dev и release включён, на prod выключен и включается точечно для одного сервиса на ограниченное время без рестарта (Spring Boot: endpoint `/actuator/loggers`, .NET: перечитывание конфигурации). Запись в отдельный индекс с хранением 3 дня |
| TRACE | Только локальная отладка, в общую систему не отправляется |
| WARN | Ситуация обработана, но требует внимания: повтор публикации или обработки, сообщение получено повторно (redelivered), медленная операция (запрос дольше 1 с, расчёт дольше 20 минут), ошибка валидации в запросе партнёра, отклонённый по лимиту запрос, приближение к лимитам (пул соединений) |
| ERROR | Операция не выполнена и это влияет на заказ или пользователя: не удалось опубликовать сообщение, обработка ушла в DLQ, ошибка S3 или базы, необработанное исключение. Обязательны стек и `order_id`, если он известен. Исключение логируется один раз на границе обработки, а не на каждом слое |
| FATAL (CRITICAL) | Сервис не может работать: не удалось подключиться к базе или брокеру при старте, невалидная конфигурация. Приводит к остановке процесса и алерту. В Logback уровня FATAL нет, для Java это ERROR с маркером `FATAL`, по которому настроен алерт |

## 2. Мотивация

Разбор любой нестандартной ситуации сейчас начинается с рассказа клиента и продолжается ручным чтением двух баз. Централизованные структурированные логи дают:

1. Единую хронологию заказа: по номеру заказа видно, что и когда с ним происходило во всех трёх системах и в очереди, включая сообщения, которые были отправлены, но не получены.
2. Самостоятельность поддержки: значительную часть обращений менеджер или инженер поддержки разбирает по сохранённым поискам, не отвлекая разработчиков.
3. Данные для инцидентов и релизов: всплеск ошибок после деплоя виден за минуты, а не через жалобы; для инцидента есть точная последовательность событий.
4. Защиту: аномальные потоки запросов от партнёров или злоумышленников видны по логам доступа.

Метрики, на которые повлияет внедрение:

| Метрика | Тип | Ожидание |
| --- | --- | --- |
| Время разбора обращения по заказу (от обращения до объяснения причины) | техническая и бизнес | с часов до 10-15 минут |
| Доля обращений, закрытых поддержкой без привлечения разработчиков | бизнес | с почти нуля до 60-70 % |
| Время обнаружения регрессии после релиза (рост ERROR по сервису) | техническая | минуты вместо дней; позволяет релизить чаще |
| Число обращений «где мой заказ» на 100 заказов | бизнес | снижение за счёт проактивного разбора застрявших заказов |
| Время ответа партнёру по инциденту интеграции (по `request_id` и `partner_id`) | бизнес | часы вместо дней; основа для SLA |
| Число незамеченных потерь сообщений (по парным событиям published и processed) | техническая | измеряется и стремится к нулю |

## 3. Что настраивать в первую очередь: логирование и трейсинг

Команда не сможет одновременно покрыть все системы, поэтому порядок такой:

1. **CRM API и MES API, участок интеграции через RabbitMQ и смены статусов.** Именно здесь заказы теряются и зависают, это подтверждают жалобы и клиентов, и партнёров. Логи публикации и обработки сообщений с `order_id` и `message_id` сразу позволяют находить потери простым сравнением. Трейсинг подключается в этих же двух сервисах и в том же порядке: одна библиотека (OpenTelemetry) добавляет в логи `trace_id`, поэтому делать логи и трассы раздельно нет смысла.
2. **Партнёрский API в MES API.** Ежедневные жалобы партнёров, невозможность связать запрос партнёра с заказом. Логи доступа с `partner_id` и `request_id`, который возвращается партнёру в ответе.
3. **Shop API.** Создание заказа и загрузка файла. Проблем здесь меньше, но без этих логов история заказа начинается не с начала. Трейсинг Shop API даёт явный переход в CRM через `submit_trace_id`.
4. **Логи RabbitMQ и PostgreSQL.** Закрытие каналов по таймауту и медленные запросы объясняют причины того, что видно в логах приложений.
5. **Фронтенды.** Ошибки в браузере, позже.

Трейсингом покрываются только Shop API, CRM API и MES API; RabbitMQ и базы отдельно не инструментируются, они видны как спаны внутри сервисов.

## 4. Предлагаемое решение

### 4.1. Технологии и компоненты

| Компонент | Решение | Комментарий |
| --- | --- | --- |
| Формат логов | Структурированный JSON с единой схемой полей (раздел 1.1) | Java: Logback с logstash-logback-encoder, поля `trace_id`, `span_id`, `order_id` через MDC. C#: Serilog с CompactJsonFormatter, обогащение через LogContext. Схема полей описана в общем документе и проверяется на код-ревью |
| Запись на хосте | Файлы с ротацией (по 100 МБ, хранить 5 файлов), при переходе в контейнеры вывод в stdout | Локальные файлы страхуют от недоступности системы сбора |
| Агент сбора | Fluent Bit на каждой ВМ приложений и на ВМ RabbitMQ | Читает файлы, разбирает JSON, добавляет `host`, `env`, буферизует на диске при недоступности хранилища, отправляет по HTTPS с учётной записью только на запись |
| Хранилище и поиск | Yandex Managed Service for OpenSearch плюс OpenSearch Dashboards | Управляемый сервис снимает сопровождение кластера с единственного DevOps-инженера; полнотекстовый поиск по номеру заказа, идентификатору сообщения, тексту ошибки; политики жизненного цикла индексов (ISM); плагины Alerting и Anomaly Detection; лицензия Apache 2.0 |
| Логи Managed PostgreSQL | Yandex Cloud Logging (доступны из консоли и API); медленные запросы дополнительно через pg_stat_statements в мониторинге | При необходимости позже экспорт в OpenSearch через Data Streams |
| Связь с метриками и трассами | Datasource OpenSearch в Grafana, ссылка по `trace_id` в Tempo и обратно | Разбор инцидента идёт из одного интерфейса |
| Сохранённые поиски и дашборды | «Путь заказа» (по `order_id`), «Запросы партнёра» (по `partner_id`), «Ошибки за релиз» (по `version`), «Сообщения без обработки» | Поддержка пользуется ими без знания языка запросов |

### 4.2. Доработки систем

- Shop API, CRM API: перевести логирование на JSON-энкодер, добавить MDC-фильтр, который кладёт `request_id`, `order_id`, `trace_id` в каждую запись внутри обработки запроса и сообщения, добавить события из раздела 1.1 в местах смены статусов и работы с очередью.
- MES API: Serilog с JSON, middleware для `request_id` и `partner_id`, события расчёта и обработки сообщений, возврат `request_id` партнёру в заголовке ответа.
- RabbitMQ: уровень логирования брокера info, логи соединений и каналов в файл, который читает Fluent Bit.
- DevOps: кластер OpenSearch (три узла данных, диски по 200 ГБ на старте), шаблоны индексов с явным маппингом полей, политики ISM, роли и SSO, Fluent Bit через Ansible, алерты из раздела 6.

Порядок: кластер и агент (DevOps, 4 дня), CRM API (Java, 3 дня), MES API (C#, 4 дня), Shop API (Java, 2 дня), сохранённые поиски и обучение поддержки (1 день), алерты и детекторы аномалий (DevOps, 3 дня).

## 5. Политика безопасности

### 5.1. Чувствительные данные

| Категория | Правило |
| --- | --- |
| Персональные данные покупателей (ФИО, телефон, почта, адрес доставки) | В логи не пишутся. Покупатель представлен внутренним идентификатором. Адрес и контакты живут только в базе CRM |
| Секреты (пароли, токены, ключи API, cookie, заголовок Authorization) | Никогда не логируются. В Serilog и Logback настроены фильтры, которые заменяют значения полей из запрещённого списка на `***`, плюс регулярные выражения на телефон и почту как страховка |
| Тела запросов и файлы моделей | Не логируются. Для файла пишутся только идентификатор, размер и контрольная сумма |
| Данные партнёров | Только идентификатор партнёра и технические поля запроса; коммерческие условия не логируются |
| Данные сотрудников | Идентификатор учётной записи, без ФИО |
| Тексты SQL | Только на DEBUG и без значений параметров |

Классификация: логи считаются внутренней конфиденциальной информацией. Поскольку персональные данные в них не попадают, по нашей оценке система логирования не становится хранилищем ПДн по 152-ФЗ (позицию нужно подтвердить с юристом при формализации политики), а требования к доступу и хранению применяются как к внутренним данным компании.

### 5.2. Доступ

| Роль | Кто | Права |
| --- | --- | --- |
| Поддержка | Продакт-менеджер как ответственный за поддержку, менеджеры по продажам при необходимости | Чтение индексов приложений prod уровня INFO и выше, сохранённые поиски и дашборды; DEBUG-индексы недоступны |
| Разработчики | Java, C#, фронтенд, QA, тимлид | Чтение всех индексов dev и release, чтение prod без DEBUG; создание сохранённых поисков |
| DevOps | DevOps-инженер, архитектор | Администрирование кластера, политики, роли, аудит |
| Агенты сбора | Fluent Bit | Отдельная учётная запись на окружение, только запись в свои индексы |

Вход в OpenSearch Dashboards только через корпоративный SSO с MFA; локальные учётные записи отключены, кроме аварийной административной, которая хранится в сейфе секретов. Доступ отзывается вместе с учётной записью в IdP. Кластер и Dashboards доступны только из корпоративной сети или VPN, трафик по TLS, диски зашифрованы средствами managed-сервиса. Аудит-лог доступа к Dashboards и API включён и хранится год. Права пересматриваются раз в квартал. Экспорт логов наружу (партнёрам, подрядчикам) запрещён без согласования, при передаче выгрузка обезличивается.

## 6. Политика хранения

Индексы разделены по системе, окружению и дню, чтобы политики жизненного цикла и права доступа задавались независимо:

| Индекс | Содержимое | Горячее хранение (SSD) | Общий срок | Далее |
| --- | --- | --- | --- | --- |
| `logs-shop-api-prod-YYYY.MM.DD`, `logs-crm-api-prod-*`, `logs-mes-api-prod-*` | События приложений уровня INFO и выше | 14 дней | 90 дней | Снимок в Object Storage, хранение 1 год, затем удаление |
| `logs-access-{service}-prod-*` | HTTP access-логи | 7 дней | 30 дней | Удаление |
| `logs-errors-prod-*` | Копия записей WARN и выше из всех сервисов (маршрутизация в Fluent Bit) | 30 дней | 180 дней | Снимок, 1 год |
| `logs-debug-{service}-{env}-*` | DEBUG | 3 дня | 3 дня | Удаление |
| `logs-rabbitmq-prod-*`, `logs-infra-prod-*` | Логи брокера и системные | 7 дней | 60 дней | Удаление |
| `logs-*-dev-*`, `logs-*-release-*` | Все уровни на тестовых окружениях | 7 дней | 7 дней | Удаление |

Оценка объёма (предположения: суммарно около 10 запросов в секунду на три API, средняя запись 1 КБ, около 150 событий на заказ во всех системах, 2-3 тысячи заказов в месяц):

- события приложений: до 0,2 ГБ в день (событий по заказам немного, основной объём дают периодические задания и обработчики сообщений);
- access-логи: около 0,9 ГБ в день;
- брокер, инфраструктура, ошибки: до 0,3 ГБ в день;
- итого около 1,2-1,5 ГБ в день первичных данных; индекс OpenSearch раздувает объём примерно в полтора раза, плюс одна реплика, итого 3,5-4,5 ГБ в день на дисках. С учётом сроков хранения (90 дней для приложений, 30 для access-логов, 60 для брокера и инфраструктуры) кластеру нужно около 200 ГБ, с запасом на рост 300 ГБ, что укладывается в три узла по 200 ГБ. Рост линейный, объём пересматривается раз в квартал вместе с ростом заказов.

## 7. От сбора логов к анализу

### 7.1. Алертинг по логам

Через плагин Alerting в OpenSearch (мониторы по запросу раз в минуту, уведомления в Telegram и в Alertmanager из мониторинга, чтобы каналы эскалации были общие):

| Условие | Уровень | Действие |
| --- | --- | --- |
| Запись `message.dead_lettered` | warning, при более 10 за час critical | Тикет поддержке на разбор в тот же день, при массовых попаданиях звонок дежурному: каждое сообщение соответствует шагу заказа. Пороги те же, что в плане мониторинга |
| Записей ERROR по сервису больше 20 за 5 минут или в 3 раза больше среднего за час | warning, при росте до 100 critical | Тикет; проверка последнего релиза |
| `calc.finished` с результатом ошибка или таймаут больше 5 за час | warning | Тикет C#-разработчику, список заказов в алерте |
| Доля кодов 5xx партнёрского API больше 1 % за 5 минут | warning, при более 5 % critical | Тикет, при critical звонок дежурному (пороги совпадают с планом мониторинга) |
| Всплеск 4xx по одному `partner_id` | warning | Уведомление партнёру и менеджеру: сломалась интеграция на его стороне |
| Нет событий `order.created` два часа в рабочее время | warning | Проверка магазина и партнёрского API |
| `message.published` без парного `message.received` в течение 15 минут | critical | Сообщение не дошло до обработчика; список идентификаторов сообщений и заказов в алерте |
| `message.received` без `message.processed` дольше 60 минут | warning | Обработка зависла (норма расчёта до 30 минут) |
| FATAL или `app.stopped` без последующего `app.started` за 2 минуты | critical | Звонок дежурному |
| Ошибки записи у Fluent Bit, переполнение буфера | warning | DevOps: система логирования слепнет |

### 7.2. Поиск аномалий

Плагин Anomaly Detection в OpenSearch (алгоритм Random Cut Forest) обучается на исторических рядах и отмечает отклонения без ручных порогов. Детекторы:

1. Число `order.created` в минуту с разбивкой по источнику. Пример из условия: было четыре записи о создании заказов, за секунду стало 10 000. Это либо DDoS, либо сломанный клиент партнёра, либо ошибка в нашем коде (цикл повторов). Действие: алерт critical, ручная проверка партнёра, временное ограничение ключа партнёра (после появления шлюза лимит включается автоматически).
2. Число запросов партнёрского API в минуту по каждому `partner_id` и по адресу источника.
3. Число ERROR в минуту по сервису (ловит регрессии после релиза без ручного порога).
4. Средний размер загружаемых файлов и число загрузок в час (аномально большие файлы способны выесть CPU на расчётах).
5. Длительность расчёта стоимости и время подхвата заказа CRM (рост латентности до того, как он станет заметен).

Помимо детекторов, раз в неделю формируется отчёт по логам: топ ошибок, заказы с ошибками, партнёры с наибольшей долей отклонённых запросов. Отчёт обсуждается на планировании спринта, чтобы логи влияли на приоритеты, а не только на разбор инцидентов.

## 8. Дополнительное задание: критерии выбора технологии

| Критерий | ELK (Elastic Stack) | OpenSearch (Yandex Managed) | Grafana Loki | Splunk | ClickHouse-решения (SigNoz, Uptrace) |
| --- | --- | --- | --- | --- | --- |
| Лицензия и доступность в РФ | Elastic License 2.0 и SSPL, с версии 8.16 также AGPLv3; вендор ушёл с рынка РФ | Apache License 2.0, есть managed-сервис у российского провайдера | AGPL v3, бесплатно, вендор ушёл с рынка РФ, но самостоятельная установка доступна | Проприетарная, продажи и поддержка в РФ прекращены | Apache 2.0 (ClickHouse), интерфейсы под собственными лицензиями |
| Сопровождение силами одного DevOps | Собственный кластер, обновления и бэкапы на команде | Managed: обновления, бэкапы, мониторинг у провайдера | Несколько компонентов (distributor, ingester, querier), настройка требует опыта | Тяжёлая установка, обычно отдельный администратор | Кластер ClickHouse плюс UI, опыт в команде отсутствует |
| Полнотекстовый поиск и язык запросов | Полный, KQL и Lucene | Полный, тот же синтаксис, PPL и SQL | Поиск по меткам, полнотекстовый только внутри отфильтрованного потока (grep-подобный) | Полный, SPL, очень мощный | SQL, полнотекстовый ограничен |
| Стоимость хранения | Индекс раздувает объём в 1,5-2 раза, SSD на горячих узлах | То же, но тарификация managed-сервиса и тиринг через ISM | Самая низкая: индексируются только метки, данные в Object Storage | Лицензия по объёму ингеста, самая дорогая | Низкая, сильное сжатие |
| Интеграция с метриками и трассами (Grafana, Tempo) | Datasource в Grafana | Datasource в Grafana, ссылка по `trace_id` | Нативная, лучшая в Grafana | Собственная экосистема | Собственный UI, экспорт в Grafana ограничен |
| Встроенные алертинг и поиск аномалий | Alerting и ML в платных тирах | Плагины Alerting и Anomaly Detection бесплатно | Правила LogQL через Ruler, аномалий нет | Мощная аналитика, дорого | Базовые алерты |
| Безопасность: RBAC, SSO, аудит | В платных тирах или ограниченно | Security-плагин: роли, SAML/OIDC, аудит, шифрование | Через Grafana, разграничение по тенантам, аудит ограничен | Полный набор | Ограниченно |
| Навыки команды | Синтаксис знаком многим | Тот же, порог входа низкий | LogQL новый для команды, похож на PromQL | Новый язык SPL | SQL знаком, но эксплуатация ClickHouse нет |

Итог: **Yandex Managed Service for OpenSearch**. Решающие критерии: свободная лицензия и managed-сервис у текущего облачного провайдера (единственный DevOps), полнотекстовый поиск для поддержки, бесплатные алертинг и поиск аномалий, RBAC и SSO из коробки. Минусы принимаются осознанно: индекс дороже по диску, чем Loki, и кластер из трёх узлов стоит заметных денег; при росте объёмов access-логи можно перевести в Loki с хранением в Object Storage, оставив в OpenSearch события заказов. Loki остаётся вторым кандидатом: он дешевле и лучше сочетается с Grafana и Tempo, но требует больше сопровождения и хуже подходит поддержке, которой нужен поиск по любому тексту. ELK отпадает из-за лицензии и ухода вендора, Splunk из-за цены и недоступности, ClickHouse-решения из-за отсутствия опыта в команде.
