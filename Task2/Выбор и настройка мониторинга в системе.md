# Выбор и настройка мониторинга в системе

Технический документ по внедрению мониторинга в системе «Александрит». Схема компонентов мониторинга: [alexandrite-monitoring.png](diagrams/alexandrite-monitoring.png) (исходник [alexandrite-monitoring.drawio](diagrams/alexandrite-monitoring.drawio)).

## 1. Мотивация

Сейчас единственным источником данных о работе системы остаётся Яндекс Метрика. Она видит поведение посетителей на фронтенде магазина и ничего не знает о Shop API, CRM, MES, RabbitMQ и о заказах, которые приходят через партнёрский API. Поэтому о любой проблеме команда узнаёт от клиентов, а разбор занимает часы.

Что даст мониторинг бизнесу:

1. Проблемы становятся видны раньше клиентов. Очередь расчётов растёт, сообщения уходят в DLQ, ошибки партнёрского API превышают норму: всё это видно за минуты, а не через недели по жалобам. Для компании, которая уже потеряла несколько крупных контрактов из-за «пропавших» заказов, такой мониторинг напрямую защищает выручку.
2. Появляется ответ на вопрос «где заказы». Метрики по статусам заказов и времени в каждом статусе показывают, на каком шаге процесс останавливается. Это снимает часть нагрузки с менеджеров по продажам и поддержки.
3. Планирование мощностей вместо аварийного тушения. Нагрузка растёт линейно (плюс 100 заказов в месяц) и скачками (подключение партнёров). Тренды по CPU, очередям и базе позволяют добавлять ресурсы заранее, а не когда упало.
4. Измеримость изменений. Дальше команда будет менять интеграцию через очередь, выносить расчёт стоимости, вводить кеш. Без базовых метрик нельзя доказать, что изменение помогло, и нельзя безопасно релизить чаще.
5. Основа для SLA партнёрам. Чтобы обещать партнёрам время ответа и время создания заказа, эти величины нужно измерять.

Стоимость: одна ВМ под стек мониторинга (или managed-сервис), около трёх недель работы DevOps-инженера, по несколько дней у Java- и C#-разработчиков на подключение библиотек и бизнес-метрик. Это заметно дешевле одного потерянного контракта.

## 2. Анализ системы в контексте мониторинга

| Компонент | Тип | Что важно знать | Откуда брать метрики |
| --- | --- | --- | --- |
| Shop API (Spring Boot) | Сервис, обслуживает запросы | Скорость и ошибки создания заказов и загрузки файлов | Spring Boot Actuator + Micrometer |
| CRM API (Spring Boot) | Сервис + consumer/producer RabbitMQ | Ошибки обработки сообщений, время подтверждения заказов | Micrometer, метрики обработчика |
| MES API (C#) | Сервис + consumer + тяжёлые вычисления | Длительность и очередь расчётов, латентность дашборда, партнёрские запросы | prometheus-net или OpenTelemetry .NET |
| Internet Shop, CRM, MES (SPA) | Фронтенды | Ошибки в браузере, скорость загрузки | Яндекс Метрика (магазин), позже RUM; в первую очередь не входят |
| RabbitMQ | Брокер | Глубина очередей, неподтверждённые сообщения, DLQ, наличие обработчиков | Плагин rabbitmq_prometheus |
| Shop DB, MES db (Managed PostgreSQL) | Хранилище | Соединения, память, диск, медленные запросы | Yandex Monitoring (метрики managed-сервиса), при необходимости postgres_exporter |
| 3D files storage (S3) | Хранилище объектов | Объём, ошибки запросов | Метрики Object Storage в Yandex Monitoring |
| ВМ приложений и RabbitMQ | Инфраструктура | CPU, память, диск, сеть | node_exporter |
| Партнёрский API (часть MES API) | Внешний интерфейс | Нагрузка и ошибки по каждому партнёру | Метрики MES API с меткой партнёра |

Общий вывод: у системы три класса объектов. Сервисы, которые отвечают на запросы (RED-подход), ресурсы, которые расходуются (USE-подход), и сквозной бизнес-процесс заказа, для которого стандартных методик нет и нужны собственные метрики.

## 3. Выбор подхода к мониторингу

Для разных частей системы используются разные подходы:

| Часть системы | Подход | Почему |
| --- | --- | --- |
| Shop API, CRM API, MES API, партнёрский API | Четыре золотых сигнала: латентность, трафик, ошибки, насыщенность. По сути это RED (Rate, Errors, Duration) плюс насыщенность | Это сервисы, обслуживающие запросы; RED отвечает на вопрос «хорошо ли сервису с точки зрения пользователя», насыщенность добавляет прогноз «когда станет плохо» |
| Обработчики RabbitMQ в CRM API и MES API | RED применительно к обработке сообщений | Обработка сообщения ничем не отличается от запроса: сколько обработали, сколько с ошибкой, за сколько |
| ВМ, PostgreSQL, RabbitMQ как ресурс, S3 | USE (Utilization, Saturation, Errors) | Это ресурсы; для них важно, насколько они заняты, есть ли очередь за ними и есть ли ошибки |
| Процесс заказа | Бизнес-метрики процесса: количество заказов по статусам, время в статусе, застрявшие заказы, доля потерянных | Ни RED, ни USE не покажут заказ, который лежит в SUBMITTED три недели. Для этого нужны метрики самого процесса |

## 4. Метрики

Ниже метрики из предложенного списка, решение по каждой и ярлыки (labels). Общие ярлыки для всех метрик приложений: `service` (shop-api, crm-api, mes-api), `env` (dev, release, prod), `instance`. Они добавляются на уровне сбора и в таблице не повторяются.

### 4.1. RabbitMQ

| Метрика | Берём | Зачем | Ярлыки |
| --- | --- | --- | --- |
| Number of dead-letter-exchange letters | Да | Каждое сообщение в DLQ это, скорее всего, потерянный заказ или статус. Единственная метрика, по которой уместен алерт при значении больше нуля | `queue` (имя DLQ), `vhost` |
| Number of messages in flight | Да, раздельно ready и unacked | Ready растёт: обработчики не успевают или их нет. Unacked растёт: обработчики взяли сообщения и не подтверждают (зависший расчёт, упавший процесс) | `queue`, `state` (ready, unacked), `vhost` |
| Дополнительно: число обработчиков на очереди | Да | Очередь без обработчиков означает тихую потерю заказов | `queue` |
| Дополнительно: скорость publish/deliver/redeliver | Да | Redeliver показывает повторы после сбоев и таймаутов | `queue` |
| Дополнительно: возраст самого старого сообщения | Да | Прямой сигнал «сколько ждёт заказ», понятнее глубины очереди | `queue` |
| Дополнительно: тревоги брокера по памяти и диску, число соединений | Да | При срабатывании тревоги RabbitMQ блокирует отправителей, и снаружи это выглядит как зависшие сервисы | `node` |

### 4.2. API-сервисы (RED)

| Метрика | Берём | Зачем | Ярлыки |
| --- | --- | --- | --- |
| Number of requests (RPS) для Shop API, CRM API, MES API | Да, как счётчик запросов (в Micrometer это таймер `http.server.requests`, из которого берутся count и sum, в prometheus-net отдельный счётчик) | Трафик: базовая линия для планирования и для интерпретации остальных метрик | `route` (шаблон пути, не сырой URL), `method`, `status` (код ответа) |
| Number of HTTP 200 и HTTP 500 для трёх API | Да, но не как отдельные метрики, а через ярлык `status` того же счётчика | Доля ошибок 5xx считается запросом `sum(rate(5xx))/sum(rate(all))`. Отдельные счётчики на каждый код избыточны, а 4xx для партнёрского API тоже нужны (ошибки в запросах партнёров) | `route`, `method`, `status` |
| Response time (latency) для трёх API | Да, как гистограмма | p50/p95/p99 по маршрутам. Для дашборда MES именно она отражает жалобу операторов; для партнёрского API основа SLA | `route`, `method`; ярлык `status` не добавляем, чтобы не множить корзины гистограммы |
| Number of requests per user для MES API | Да, только для маршрутов партнёрского API | Партнёров немного, для них нужны квоты и разбор «кто нас завалил». Кардинальность контролируемая | `partner_id` (идентификатор учётной записи партнёра, после появления шлюза ключа API), `route` |
| Number of requests per user для Shop API и CRM API | Нет | Покупателей тысячи, ярлык с их идентификатором взорвёт кардинальность, а решения по этой метрике не принимаются. Поведение отдельных пользователей разбирается по логам |  |
| Number of simultaneous sessions | Да для Internet Shop (через Shop API) и MES; для CRM с низким приоритетом | Для магазина она показывает активных покупателей (бизнес-показатель и нагрузка на загрузку моделей). Для MES она показывает число операторов, работающих одновременно, то есть загрузку производства. В CRM продавцов мало, метрика почти бесполезна, но стоит копейки | `service` |
| Kb transferred (received) для Shop API и MES API | Да | Оба принимают 3D-файлы. Рост объёма служит ранним признаком нагрузки на сеть и S3, а всплеск указывает на злоупотребление API | `route` (только маршруты загрузки файлов) |
| Kb transferred для CRM API, Kb provided (sent) для всех API | На уровне ВМ через node_exporter (байты по интерфейсам), не на уровне приложения | Полезно для насыщенности сети, но детализация по маршрутам ничего не добавляет | `instance`, `device` |

### 4.3. Ресурсы (USE)

| Метрика | Берём | Зачем | Ярлыки |
| --- | --- | --- | --- |
| CPU % для ВМ Shop API, CRM API, MES API | Да | Насыщенность. Для MES API она ещё и показывает, сколько CPU съедают расчёты стоимости | `instance`, `mode` |
| Memory utilisation для ВМ трёх API | Да | Утечки и неправильные лимиты. Дополнительно память JVM (heap after GC) для Java и размер кучи .NET для MES API | `instance`; для приложений `area` (heap, nonheap) |
| Memory utilisation для инстансов Shop DB и MES db | Да | Падение эффективности кеша страниц заметно раньше, чем запросы станут медленными | `cluster`, `host` |
| Number of connections для Shop DB и MES db | Да, с разбивкой по состоянию | Исчерпание max_connections останавливает оба API, работающих с Shop DB. Соединения `idle in transaction` показывают ошибки в коде | `cluster`, `database`, `state` (active, idle, idle_in_transaction) |
| Size of Shop DB и MES db | Да | Планирование диска и индикатор роста таблиц заказов и истории статусов | `cluster`, `database` |
| Size of S3 storage | Да, раз в час или реже | Стоимость и планирование, а не алертинг. Дополнительно число объектов и ошибки запросов | `bucket` |
| Дополнительно: диск ВМ, iowait, load average, сеть | Да | Стандартный набор node_exporter, дешёвый и нужный для разбора инцидентов | `instance` |
| Дополнительно: медленные запросы PostgreSQL, cache hit ratio, deadlocks, TPS | Да | Разбор жалоб на дашборд MES без метрик базы невозможен | `cluster`, `database` |

### 4.4. Дополнительные метрики процесса заказа

Этих метрик в списке нет, но именно они отвечают на главный вопрос бизнеса.

| Метрика | Тип | Зачем | Ярлыки |
| --- | --- | --- | --- |
| `orders_by_status` | gauge, пересчитывается раз в минуту запросом к Shop DB (CRM API) и MES db (MES API) по индексу (статус, дата создания), который в любом случае нужен дашборду | Сколько заказов в каждом статусе. Расхождение между картиной CRM и MES сигнализирует о потере сообщений | `status`, `source` (shop, api), `system` (crm, mes) |
| `order_status_transitions_total` | counter | Скорость прохождения процесса, доля заказов, доходящих до следующего шага | `from_status`, `to_status`, `system` |
| `order_stage_duration_seconds` | histogram | Время в каждом статусе. Основа для SLA «расчёт за час, производство за три недели» | `stage` |
| `orders_stuck` | gauge, публикует задание сверки в CRM API (в решении по трейсингу оно названо Order Flow Monitor) | Заказы, находящиеся в статусе дольше нормы шага (например, SUBMITTED дольше 60 минут без расчёта). Главный алерт для бизнеса | `stage` |
| `price_calculation_duration_seconds` | histogram | Длительность расчётов, отдельно по источнику и размеру модели; показывает, когда пора масштабировать воркеры | `source`, `size_bucket` (по числу полигонов) |
| `price_calculation_failures_total` | counter | Ошибки расчёта, отдельно по причине | `reason` (timeout, bad_model, storage_error, other) |
| `message_processing_duration_seconds`, `message_processing_failures_total` | histogram, counter | RED для обработчиков очереди | `queue`, `result` |
| `app_build_info` | gauge со значением 1 | Версия приложения как ярлык: позволяет сопоставить проблему с релизом | `version`, `commit` |
| `probe_success` (blackbox_exporter) | gauge | Доступность каждого API, фронтендов и панели RabbitMQ снаружи процесса | `target` |

## 5. Инструменты

- Сбор и хранение метрик: Prometheus на отдельной ВМ (2 vCPU, 8 ГБ, диск 100 ГБ, хранение 30 дней). Альтернатива с меньшими затратами на сопровождение: Yandex Monitoring с его Prometheus-совместимым API. Выбран Prometheus, потому что нужен единый стек с трейсингом и логами (Grafana), а объём метрик небольшой.
- Визуализация: Grafana с дашбордами как код (provisioning из git).
- Алертинг: Alertmanager, маршрутизация по severity: warning в Telegram-канал и тикет, critical в Telegram плюс телефонный звонок дежурному через webhook Alertmanager во внешний сервис оповещений (сам Alertmanager звонить не умеет).
- Экспортёры: node_exporter на всех ВМ, rabbitmq_prometheus (встроенный плагин), blackbox_exporter, метрики Managed PostgreSQL и Object Storage из Yandex Monitoring через datasource в Grafana (при нехватке детализации: postgres_exporter с pg_stat_statements).
- Приложения: Spring Boot Actuator с Micrometer (Shop API, CRM API), prometheus-net или OpenTelemetry .NET SDK с Prometheus-экспортером (MES API).

Итого около четырёх недель календарного времени при 60 % занятости DevOps-инженера и суммарно около двух недель времени разработчиков.

Ограничения безопасности: Grafana доступна только через корпоративный SSO и VPN, Prometheus и экспортёры слушают только приватные адреса, в ярлыках метрик нет персональных данных (только идентификаторы заказов, партнёров и маршруты).

## 7. Дополнительное задание: показатели насыщенности и пороги

Насыщенность отвечает на вопросы «насколько полон ресурс» и «сколько ждут в очереди за ним». Пороги ниже выбраны так, чтобы оставался запас времени на реакцию: новая ВМ или воркер поднимается за 5-10 минут, а ручное вмешательство дежурного занимает до получаса.

| Показатель | Warning | Critical | Почему такие значения | Действие |
| --- | --- | --- | --- | --- |
| CPU ВМ приложения | более 70 % в среднем 10 минут | более 85 % 5 минут | Выше 70 % латентность начинает расти нелинейно, а 15 % запаса хватает, чтобы успеть добавить мощность | Warning: тикет и запись в канал, план масштабирования. Critical: звонок дежурному; для stateless-сервисов после появления групп автомасштабирования добавление экземпляра автоматически; для MES API до выноса расчётов вертикальное увеличение ВМ |
| Память ВМ, heap JVM после GC, куча .NET | более 80 % | более 90 % | На 90 % начинаются свопинг или OOM-kill | Warning: тикет на разбор утечки или лимитов. Critical: звонок, рестарт сервиса по runbook |
| Диск ВМ и диск инстанса PostgreSQL | более 75 % | более 90 % | Рост базы линейный и предсказуемый, 25 % запаса даёт недели на расширение | Warning: тикет на расширение диска (для managed PostgreSQL расширяется без остановки). Critical: звонок, расширение немедленно |

Правила эскалации: warning всегда оставляет след в тикете и канале, чтобы повторяющиеся предупреждения было видно; critical звонит дежурному, а если дежурный не подтвердил алерт за 15 минут, звонок уходит тимлиду. Автоматические действия (добавление экземпляра, рестарт) допускаются только для stateless-компонентов и только после того, как для них написан и проверен runbook.
