# Планирование: анализ, идентификация проблем и поиск решений

Кейс компании «Александрит». Документ фиксирует, как устроена система сейчас, где она ломается, какие инициативы нужны и в каком порядке их выполнять.

Схемы: [текущая архитектура (C4, контейнеры)](diagrams/alexandrite-as-is.png), [целевая архитектура через полгода](diagrams/alexandrite-target-6m.png) (исходник [alexandrite-target-6m.drawio](diagrams/alexandrite-target-6m.drawio)).

## 1. Как устроена система сейчас

Три приложения, каждое в одном экземпляре на отдельной ВМ, базы данных в managed-сервисе Yandex Cloud, тоже по одному инстансу на чтение и запись:

| Часть системы | Технологии | Хранилище | Роль в процессе заказа |
| --- | --- | --- | --- |
| Онлайн-магазин (Internet Shop + Shop API) | Vue, Three.js, Spring Boot | Shop DB (PostgreSQL), 3D-файлы в S3 | Создание заказа, загрузка или сборка 3D-модели, статусы INITIATED, FILE_UPLOADED, SUBMITTED |
| CRM (CRM + CRM API) | Vue, Spring Boot | Та же Shop DB | Подтверждение производства (MANUFACTURING_APPROVED), закрытие заказа (CLOSED), общение продавцов с клиентами |
| MES (MES + MES API) | React, C# | MES db (PostgreSQL), читает 3D-файлы из S3 | Расчёт стоимости (PRICE_CALCULATED), производство и отгрузка (MANUFACTURING_STARTED ... SHIPPED), дашборд операторов |
| Очередь сообщений | RabbitMQ, несколько топиков | | Обмен событиями между CRM API и MES API, интеграция написана командой |

Ключевые наблюдения по схеме, которые дальше определяют список проблем:

1. У заказа нет одного хозяина. Статус меняют три системы, данные лежат в двух базах (Shop DB и MES db), а единственной связью между ними служит самописная интеграция через RabbitMQ. Никакой сверки между базами нет.
2. Shop API и CRM API работают с одной базой. Это неявная интеграция «через таблицы»: магазин пишет заказ, CRM его читает и отправляет в MES. Такой переход нигде не виден как событие, поэтому его нельзя ни отследить, ни повторить.
3. Расчёт стоимости (2-3 минуты, до 30 минут на сложных моделях) выполняется внутри MES API. Тот же процесс обслуживает интерфейс операторов и внешних пользователей API. Инстанс один.
4. Партнёрский API открыт прямо на MES API, без шлюза. B2B-заказ рождается в производственной системе и попадает в CRM «задом наперёд», через очередь. Это второй, независимый путь создания заказа со своими точками отказа.
5. Наблюдаемости нет: единственным источником данных остаётся Яндекс Метрика, которая видит только фронтенд магазина. О проблемах команда узнаёт от клиентов.
6. Релизы задерживаются больше чем на месяц из-за ручного E2E-тестирования одним QA. Любое исправление доезжает до прода медленно, поэтому все остальные проблемы живут дольше, чем могли бы.

Путь заказа и где он может сломаться:

| Шаг | Кто и как | Что может пойти не так |
| --- | --- | --- |
| SUBMITTED | Shop API сохраняет заказ в Shop DB, файл в S3 | Файл не загрузился, а заказ сохранён; заказ есть, но CRM его не подхватила |
| Заявка на расчёт | CRM API публикует сообщение в RabbitMQ | Сообщение не опубликовано (брокер недоступен, нет publisher confirms), не сохранено на диск (non-durable), потеряно при рестарте брокера |
| PRICE_CALCULATED | MES API забирает сообщение, скачивает файл, считает | Consumer упал во время расчёта; расчёт дольше таймаута подтверждения; сообщение переотправлено и посчитано дважды или ушло в никуда |
| Ответ в CRM | MES API публикует результат, CRM API обновляет Shop DB | Те же потери, что и выше; дубликаты статусов; порядок сообщений |
| MANUFACTURING_APPROVED | Продавец подтверждает в CRM, CRM API шлёт сообщение | Сообщение потеряно, заказ никогда не появится у операторов |
| Производство и отгрузка | Оператор меняет статусы в MES, MES API шлёт сообщения в CRM | CRM не видит новых статусов, клиент и менеджер думают, что заказ стоит |
| CLOSED | По сообщению от транспортной компании или вручную | Внешняя интеграция, ошибки не видны |
| B2B через API | Партнёр вызывает MES API, MES считает, CRM создаёт заказ по сообщению | Партнёр не получает ни ответа, ни статуса; при потере сообщения заказа в CRM нет вообще |

## 2. Список проблем

Проблемы разделены на те, что уже проявились, и те, что проявятся при росте (нагрузка растёт линейно, плюс 100 заказов каждый месяц, а в Q2 добавились партнёры).

### 2.1. Проявившиеся проблемы

| № | Проблема | Как проявляется | Причина (факт или гипотеза) |
| --- | --- | --- | --- |
| P1 | Заказы теряются или зависают между системами | Клиенты ждут месяцами при плане в три недели, партнёры не получают заказы, потеряны крупные контракты | Интеграция через RabbitMQ без гарантий доставки. Гипотеза: очереди и сообщения не durable/persistent, нет publisher confirms, auto-ack, нет DLQ, повторов и идемпотентности обработчиков. Сверки между Shop DB и MES db нет |
| P2 | Никто не может ответить, где заказ и почему он стоит | Разбор каждой жалобы занимает часы, о проблемах узнают от клиентов | Нет метрик, централизованных логов, трейсинга и сквозного идентификатора заказа в сообщениях |
| P3 | Расчёт стоимости конкурирует со всем остальным | Медленный дашборд операторов, задержки ответов партнёрам, растущая очередь расчётов | CPU-тяжёлый расчёт выполняется внутри MES API на единственном инстансе, без выделенного пула воркеров. Гипотеза: расчёты, близкие к 30 минутам, упираются в consumer_timeout RabbitMQ (по умолчанию 30 минут), канал закрывается, сообщение переотправляется |
| P4 | Первая страница MES грузится долго | Операторы жалуются, страдает распределение заказов и их вознаграждение | Запрос списка «новые заказы по статусам» на растущей таблице, фильтр и offset-пагинация не помогли. Гипотеза: нет составного индекса (статус, дата создания), count(*) на каждый запрос, база одна на чтение и запись и делит CPU с расчётами |
| P5 | Партнёрский API не имеет контракта и защиты | Партнёры ежедневно сообщают, что заказы не получены; MES завалена запросами | API открыт прямо на MES API: нет шлюза, лимитов, квот, ключей на партнёра, нет асинхронного ответа (статус, webhook). Заказ создаётся в CRM из MES через очередь, то есть по самому ненадёжному каналу |
| P6 | Релизы выходят с задержкой больше месяца | Исправления багов и любые из инициатив ниже доезжают до прода медленно | Ручное E2E-тестирование одним инженером, ручной деплой в release и prod, блокировка релиза на high/highest багах без возможности частичного выпуска |

### 2.2. Потенциальные и структурные проблемы

| № | Проблема | Риск |
| --- | --- | --- |
| P7 | Общая база Shop API и CRM API | Изменение схемы одной командой ломает другую систему; нагрузка CRM (отчёты, выборки) тормозит магазин; нельзя масштабировать и релизить независимо |
| P8 | Единственный экземпляр каждого приложения, RabbitMQ и баз | Любой рестарт или деплой означает простой; падение ВМ с RabbitMQ теряет сообщения в памяти; нет балансировщика и автомасштабирования |
| P9 | Нет единого источника правды о статусе заказа | Две базы с разной картиной мира, нет журнала переходов, невозможно восстановить историю или найти расхождение автоматически |
| P10 | Bus factor на MES | Один C#-разработчик на систему, которая стала точкой входа для B2B; MES куплена с исходниками, доработки превращают её в форк, обновления вендора становятся дорогими |
| P11 | Отсутствие лимитов на внешнем API | Один партнёр (или конкурент) может создать нагрузку, которая остановит производственную систему |
| P12 | Ручной деплой без отката и без feature flags | Каждый релиз рискованный, поэтому их делают редко, что возвращает к P6 |
| P13 | Нет уведомлений клиентам и партнёрам о смене статуса | Вопросы «где мой заказ» идут менеджерам по продажам вручную |
| P14 | Повторные расчёты одинаковых моделей | При повторной отправке той же модели (правки заказа, повторные заказы партнёра) расчёт выполняется заново, хотя результат детерминирован |

## 3. Инициативы

| № | Инициатива | Закрывает | Размер | Кто |
| --- | --- | --- | --- | --- |
| I1 | Наблюдаемость и контроль прохождения заказа: метрики (RED/USE), централизованные логи, трейсинг с идентификатором заказа в HTTP-заголовках и заголовках AMQP, журнал переходов статусов, алерт «заказ застрял дольше нормы» | P1, P2, P9 | M | DevOps, по одному Java- и C#-разработчику |

| I3 | Вынос расчёта стоимости в отдельный сервис-воркер: своя очередь задач, пул воркеров на CPU-оптимизированных ВМ, масштабирование по глубине очереди, отдельные очереди для быстрых и тяжёлых моделей, MES API только ставит задачу и отдаёт статус | P3, P4, P5 | M-L | C# (нужен второй), DevOps |
| I4 | Партнёрский API как продукт: шлюз (ключи, rate limiting, квоты), асинхронный контракт (202 Accepted, endpoint статуса, webhook), фасад Partner API вне MES, создание B2B-заказа через CRM API как владельца заказа | P5, P11, P13 (для партнёров) | M | Java, DevOps |
| I5 | Быстрый дашборд MES: составные индексы, keyset-пагинация, кеш первых страниц и счётчиков по статусам (Redis), позже read-реплика | P4 | S | C#, DevOps |
| I6 | CI/CD и автотесты: автоматический E2E-прогон сквозного сценария заказа, контрактные тесты на сообщения очереди, автодеплой в release, canary или blue-green на prod с откатом, feature flags | P6, P12 | M | QA (переход в автоматизацию), DevOps |
| I7 | Отказоустойчивость и масштабирование: контейнеризация, минимум два экземпляра каждого stateless-сервиса за балансировщиком (Yandex ALB), группы автомасштабирования, кластер RabbitMQ, далее Managed Kubernetes | P8 | M-L | DevOps |
| I8 | Разделение общей базы: своя база или как минимум своя схема для CRM, обмен с магазином через API и события, PgBouncer, read-реплика для отчётов | P7 | L | Java, DevOps |
| I9 | Команда: второй C#-разработчик (MES и расчёт), перевод QA в автоматизацию плюс найм ручного тестировщика, второй DevOps/SRE; назначить владельца процесса заказа как сквозного сценария | P10, P6 | | Тимлид, продакт |
| I10 | Уведомления клиентам и партнёрам о смене статуса (email, личный кабинет, webhook) | P13 | S | Java |
| I11 | Кеш результатов расчёта по хешу файла модели и параметрам заказа | P14, P3 | S | C# |

## 4. Приоритизация

Критерии, по которым расставлены инициативы:

1. Прямое влияние на потерю заказов и контрактов. Это то, что стоит компании денег прямо сейчас.
2. Является ли инициатива фундаментом для остальных. Без наблюдаемости нельзя ни проверить гипотезы из раздела 2, ни измерить эффект от любых изменений.
3. Стоимость с учётом команды: восемь человек и архитектор, три стека, один C#-разработчик на MES. Инициативы, которые опираются на C#, приходится разводить по времени.
4. Риск изменения. Настройки брокера и индексы в базе меняются за дни, разделение базы занимает месяцы.

Порядок и ход рассуждений:

1. **I1 Наблюдаемость** идёт первой. Дёшево (в основном настройки и библиотеки), даёт данные для всего остального и сразу снимает часть нагрузки с поддержки: на вопрос «где заказ» отвечает система, а не расследование. Журнал переходов статусов и алерт на застрявшие заказы дают самый быстрый способ перестать терять заказы молча.
2. **I2 Надёжная очередь**. Основная причина потерь по гипотезе P1. Первая часть (durable, confirms, ручной ack, DLQ) сводится к конфигурации и небольшим правкам кода, её можно выполнить в первые недели. Outbox и кластер брокера идут второй частью.
3. **I5 Дашборд MES** (индексы и keyset-пагинация) делается параллельно, потому что стоит дни, а операторы страдают каждый день. Кеш подключается после появления метрик, чтобы измерить эффект.
4. **I3 Вынос расчёта** и **I4 Партнёрский API** образуют вторую волну. Они снимают с MES роль «сервера всего» и дают партнёрам нормальный контракт. Они требуют второго C#-разработчика (I9), поэтому найм запускается сразу.
5. **I6 CI/CD** идёт параллельно со второй волной. Автоматический E2E сквозного сценария заказа нужен как приёмочный тест для I2 и I3, поэтому его начинают раньше остального в I6.
6. **I7 Отказоустойчивость** третья волна: после того как сервисы стали stateless и упакованы в контейнеры, добавить второй экземпляр и балансировщик уже просто.
7. **I8 Разделение базы**, **I10 Уведомления**, **I11 Кеш расчётов** завершают полугодие или уходят дальше. I8 самая дорогая и самая рискованная, её начинают с выделения схемы и запрета прямых запросов CRM в таблицы магазина, а физическое разделение делают, когда есть трейсинг и автотесты.

| Волна | Срок | Инициативы |
| --- | --- | --- |
| 1 | Месяцы 1-2 | I1, I2 (часть 1: настройки брокера, ack, DLQ, идемпотентность), I5 (индексы, пагинация), старт найма по I9 |
| 2 | Месяцы 2-4 | I2 (часть 2: outbox, кластер), I3, I4, I6 (E2E сквозного сценария, автодеплой в release) |
| 3 | Месяцы 4-6 | I7, I5 (кеш), I10, I11, I8 (первый этап: схема и API вместо прямых запросов), I6 (canary на prod) |

## 5. Целевая архитектура через полгода

Схема: [alexandrite-target-6m.png](diagrams/alexandrite-target-6m.png). Зелёным на ней отмечены новые или изменённые элементы.

Что меняется по сравнению с текущим состоянием:

- Магазин, CRM и MES остаются тремя приложениями, но каждый API работает минимум в двух экземплярах за Application Load Balancer, в контейнерах, с автомасштабированием по CPU и очереди.
- Партнёры ходят через API Gateway (ключи, лимиты, квоты) в отдельный сервис Partner API. Он принимает заказ и модель, отвечает 202 с идентификатором, отдаёт статус по запросу и через webhook. Заказ создаётся в CRM API, которая становится единственным владельцем жизненного цикла заказа и его журнала статусов.
- Расчёт стоимости выделен в сервис Price Calculation Workers на C#: очередь задач в RabbitMQ, пул воркеров на CPU-оптимизированных ВМ, масштабирование по глубине очереди, отдельная очередь для тяжёлых моделей. Результаты попадают в кеш по хешу модели.
- RabbitMQ работает кластером из трёх узлов с quorum-очередями, DLQ и явными контрактами сообщений; в каждом сообщении есть идентификатор заказа, correlation id и trace context.
- CRM получает свою схему и доступ к данным магазина только через Shop API или события; общий доступ в таблицы закрыт. Полное разделение баз запланировано на следующее полугодие.
- Redis (managed) для дашборда MES и результатов расчётов; read-реплика Shop DB для отчётов CRM.
- Платформа наблюдаемости: Prometheus и Grafana для метрик, OpenTelemetry Collector и Tempo для трейсов, OpenSearch для логов, Alertmanager с оповещениями в Telegram и телефонным звонком дежурному. Отдельный дашборд прохождения заказов и алерт на застрявшие заказы.
- CI/CD: автотесты сквозного сценария на release-окружении, автодеплой в release, деплой в prod кнопкой с canary и откатом.

Чего в полугодовой цели нет сознательно: отдельного Order Service (жизненный цикл пока остаётся в CRM API, но за фасадом и с журналом), перехода на Kafka (RabbitMQ при таких объёмах достаточно), Kubernetes (контейнеры на ВМ за балансировщиком дают нужную отказоустойчивость с меньшим порогом для одного DevOps).

## 6. Если можно сделать только три инициативы

Выбор: **I1 (наблюдаемость и контроль заказа), I2 (надёжная очередь), I3 (вынос расчёта стоимости)**.

Почему так:

- I1 и I2 напрямую закрывают причину потерь заказов и контрактов. Без I1 нельзя проверить гипотезы о причинах потерь и подтвердить, что I2 помогла. Без I2 наблюдаемость только покажет, что заказы продолжают теряться.
- I3 решает сразу три видимых симптома: медленный дашборд операторов (расчёты больше не отбирают CPU у MES API), задержки для партнёров (расчёты масштабируются отдельно) и риск таймаутов долгих расчётов. Она же даёт партнёрам асинхронную модель ответа, то есть закрывает самую болезненную часть I4 без отдельного шлюза.
- I4 целиком не выбрана, потому что шлюз с лимитами можно взять как managed-сервис (Yandex API Gateway) за несколько дней в рамках I3, а перенос точки создания B2B-заказа в CRM дождётся следующего полугодия.
- I6 не выбрана как отдельный пункт, но автоматический E2E-сценарий заказа включён в критерии приёмки I2: иначе нельзя доказать, что сообщения перестали теряться. Его делает QA-инженер, который хочет заниматься автоматизацией.
- I5 не выбрана, потому что индексы и keyset-пагинацию (два-три дня работы) стоит сделать вне списка, как локальную задачу, а необходимость кеша станет ясна после I3 и появления метрик.
- I7 и I8 важны для роста, но не устраняют текущих потерь. Пока рост нагрузки предсказуем (плюс 100 заказов в месяц и подключения партнёров, о которых известно заранее), они могут подождать до следующего полугодия.
